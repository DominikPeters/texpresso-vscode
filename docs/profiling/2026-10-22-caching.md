# Preview caching and SVG update experiments — 22 October 2026

This follows the [PNG/SVG profiling pass](2026-10-22.md). The implemented changes
cache exported pages and decoded images in the extension. The native engine and
bundle are unchanged. SVG DOM patching is an experiment, not production behavior.
The [measurement snapshot](2026-10-22-caching.json) records the observations below.

## Implemented caches

**Encoded page cache:** per preview panel, at most eight full-page frames and
8 MiB of encoded images. LRU keys include engine revision, source barrier, page,
requested width and effective render format. Source changes and engine
invalidations clear it, including rescans, theme changes and reruns. It avoids
rebuilding the display list, encoding and transferring an image for a page revisit.
The prior implementation already avoided TeX recompilation for an unchanged
compiled page; this removes the remaining native rendering work.

**Decoded image cache:** the controller hashes MIME plus exact encoded image
bytes with SHA-256. The webview retains up to four decoded images, with a 32 MiB
accounting budget for encoded bytes plus estimated decoded RGBA. SVG accounting
uses the displayed page size at device pixel ratio. This estimate is not an exact
browser/GPU memory limit; entry count also bounds retained SVG documents. Large
images can still be displayed without being cached. Eviction revokes Blob URLs;
a missing browser entry or reloaded panel receives the full bytes again.

The browser acknowledges the identities it retained. Later identical frames use
an identity reference and fresh metadata, without image IPC bytes or another
`Image.decode()` call. This works across revisions, so an undo or repeated output
can reuse an old image. Revision, source sequence, bounds, hyperlinks and
destinations always come from the latest engine frame. An identical picture does
not imply identical synchronization or link metadata.

**Inverse SyncTeX:** a cached page does not move the native viewer. If clicking
back to source needs a different native page, the controller first requests a
normal render to prepare its display list, then sends the inverse coordinates.
This work is deferred until interaction needs it. Magnifier/detail requests
already select their requested page. New and existing tests cover stale edits,
abandoned clicks, decode credit, hidden panels and SVG decode fallback.

## Page navigation measurements

Same local M1 Pro and engine as the earlier report; Chromium 155, DPR 2,
800×700 CSS-pixel preview. Sixteen fresh browser/engine sessions per side:
two repetitions × four content types × PNG/SVG. Ten-page fixtures use lipsum
and the existing 625-circle/625-segment TikZ figure. Each session includes
next → previous → next before other operations. Four immediate revisit samples
per table cell. Runs are sequential with warm TeX package/format caches; the
cache-disabled run uses harness-only overrides for both caches.

Elapsed times include the local HTTP bridge and two animation-frame callbacks
after the image swap. They measure a paint opportunity, not completed GPU work
or real VS Code IPC. This is a small comparison to verify the cache path; it is
not a new exhaustive benchmark across document lengths.

| Content | Format | Before, median ms | Cached, median ms | Cached native exports / 4 |
| --- | --- | ---: | ---: | ---: |
| sparse | PNG | 39.4 | 15.2 | 0 |
| sparse | SVG | 24.0 | 15.0 | 0 |
| dense | PNG | 48.3 | 16.1 | 0 |
| dense | SVG | 45.5 | 15.2 | 0 |
| packed | PNG | 48.4 | 15.2 | 0 |
| packed | SVG | 56.7 | 17.9 | 0 |
| tikz | PNG | 56.7 | 15.4 | 0 |
| tikz | SVG | 46.4 | 15.7 | 0 |

All **32 cached immediate revisits transferred zero image bytes** and had no
native `pipe-write` export. All 32 baseline revisits exported full images. The
cached times are largely the browser's frame cadence plus the local bridge.
The encoded cache can also help when the decoded entry has been evicted; that
case still needs browser decoding and image transfer.

The existing alternating text-edit sequence has six frames per content/codec
across both sessions. Four of six use an already decoded image, for every
content/codec. Compilation still happens: reuse is established only after the
engine produces matching bytes. This pass does not skip compiler work for undo.

## How small are SVG changes?

`scripts/profiling/svg-diff.cjs` starts a fresh headless session for each content
type, renders the first page, inserts one `z` before a marker's `aaaa`, undoes it,
then inserts `\textbf{Z}` before the first rendered text. The probe compares
actual MuPDF output, checks byte-exact reconstruction of its patches and measures
retained glyph paths with identical IDs and path data.

| Content | Full SVG bytes after letter | Exact line patch bytes / gzip | Old glyph paths retained with same IDs |
| --- | ---: | ---: | ---: |
| sparse | 111,553 | 1,238 / 442 | 35/35 |
| dense | 341,424 | 1,238 / 442 | 42/42 |
| packed | 505,059 | 1,238 / 442 | 42/42 |
| tikz | 573,321 | 1,238 / 442 | 38/38 |

Undo restored **byte-identical SVG in all four fixtures**. For the one-letter
insertion, a line-based patch is much smaller than a single contiguous replacement:
the new glyph definition and changed uses are separated by other unchanged
content. A retained DOM patch had two operations, 1,887 bytes uncompressed / 534
gzip bytes, for each fixture. Full SVG gzip sizes were about 16–59 KiB.

The earlier-font insertion retained **zero** old glyph paths under the same IDs
in all four fixtures. MuPDF assigns font IDs in encounter order with a shared
incrementing ID counter: see the pinned
[`svg_dev_text_span`](https://github.com/ArtifexSoftware/mupdf/blob/8ad45e92f0935d3d87f1db3f873086472a5e1b24/source/fitz/svg-device.c#L479).
Adding a font early can therefore rename existing glyph references throughout
a page. A patch must be optional and fall back when its size or work is broad.
The samples do not establish behavior for arbitrary paragraph reflow or all PDF
content; the text insertion was in its own marker paragraph.

## Does updating the SVG DOM help rendering?

A separate `svg-diff-browser.cjs` experiment compares full Blob-backed SVG images,
full inline SVG replacement, and precomputed updates to a retained inline SVG.
It includes seven measured insert/undo pairs after two warmup pairs per mode,
content and edit type. Every inline update is checked against the complete SVG's
element/attribute tree, including namespace-aware attributes. It is a structural
check, not pixel-by-pixel image validation.

Inputs are preloaded and patches precomputed in Python. These timings **exclude
compilation, SVG export, patch generation and transport**. Update/decode elapsed
time includes async `Image.decode()` for images, and parsing/DOM mutation for
inline SVG. It is not CPU utilization. The experiment also records two-RAF paint
opportunities, which do not establish GPU completion.

One-letter insertion/undo medians:

| Content | Image update/decode ms | Replace inline SVG ms | Patch retained DOM ms | Paint opportunity image / patch ms |
| --- | ---: | ---: | ---: | ---: |
| sparse | 5.60 | 3.70 | 0.30 | 16.70 / 14.10 |
| dense | 15.85 | 12.50 | 0.50 | 30.85 / 9.15 |
| packed | 30.90 | 21.35 | 0.75 | 40.95 / 13.55 |
| tikz | 16.00 | 10.55 | 0.45 | 25.75 / 5.45 |

Small DOM updates are promising, especially for dense text. Simply mounting and
replacing the entire inline SVG does not achieve the same result. In the font
renumbering case, the experimental patch took about **165 ms** on the nearly full
text page versus **26 ms** for an image. A small operation count is insufficient:
one operation can replace thousands of nodes or change thousands of references.

The current production preview embeds SVG using an `<img>`. A byte diff that
reconstructs another Blob still feeds a complete document to the image decoder;
it does not itself implement the retained-DOM path. Inline SVG also changes the
embedding model; the
[SVG integration specification](https://w3c.github.io/svgwg/specs/integration/)
distinguishes image-mode processing from inline SVG.

## Recommended next steps

1. Keep the two bounded caches implemented here. They improve navigation and
   repeated output without native/protocol changes or increasing TeX snapshots.
2. Prototype a retained SVG renderer with page-scoped IDs, vetted MuPDF elements
   and attributes, and support for the existing magnifier/link overlays. Send
   patches only against a confirmed base-image identity and acknowledge the new
   identity. Send fresh synchronization/link metadata independently. On a missing
   base, revision race, patch failure or broad change, use a full frame. Mount a
   fresh validated page for full-frame fallback rather than applying a huge patch.
3. Bound diff generation time, inserted bytes, affected nodes and DOM mutation
   work. The experiment's Python SequenceMatcher is an offline measuring tool,
   not a proposed production diff algorithm. Measure generating/applying patches
   together before committing to protocol or renderer changes. Stable glyph IDs
   based on font content rather than encounter order could reduce churn later.
4. Treat compiler-state reuse for undo as separate native work. A key based only
   on root-source text misses included sources, disk resources, auxiliary state,
   configuration and compiler history. The current engine maintains a linear
   snapshot stack; retaining recent branches needs dependency/state validity and
   a measured memory budget. Investigate checkpoint placement first, then whether
   one or two recent valid states can avoid repeated expensive TikZ execution.

## Validation and reproduction

Compilation, webpack and lint pass; 66 unit tests pass. All 14 real-engine tests
passed, including the new controller test that revisits a cached page and then
uses inverse SyncTeX while the native viewer is on a different page. The first
full engine run hit two existing macOS process-group teardown `EPERM` errors;
both affected upstream tests passed on targeted rerun. No lifecycle code was
changed. Tests use headless/dummy video; no native TeXpresso windows are opened.
The packaged VSIX includes the new cache asset and passes the exact payload check.

```sh
npm run compile-tests
TEXPRESSO_PROFILE_DISABLE_CACHE=1 TEXPRESSO_PROFILE_REPEATS=2 \
  npm run profile:preview:browser -- artifacts/profile-cache-before-new
# Open http://127.0.0.1:9383, Run preview profiles, then stop the server.
TEXPRESSO_PROFILE_REPEATS=2 \
  npm run profile:preview:browser -- artifacts/profile-cache-after-new
# Open/reload the dashboard and run again; stop the server before the next probe.
node scripts/profiling/svg-diff.cjs artifacts/profile-svg-diff-new
node scripts/profiling/svg-diff-browser.cjs artifacts/profile-svg-diff-new
# Open http://127.0.0.1:9384 and choose Run comparison.
```

Use `TEXPRESSO_BINARY=/absolute/path/to/texpresso` to override the existing local
preview bundle. All probes use installed local TeX Live and existing dependencies;
no packages or large binaries are downloaded. Output directories must be new.
