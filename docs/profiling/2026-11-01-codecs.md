# PNG, SVG and Auto after shared engine updates — 1 November 2026

The new zlib-ng backend reduces full PNG export time by **34–45%** on these
fixtures at about 1600 pixels wide. Ordinary small typing updates remain close
across modes because PNG already sends tiny dirty rectangles and outlined SVG
uses small DOM patches. Mixed raster/vector documents currently favor PNG/Auto
for typing: embedded images fall outside the retained SVG DOM subset.

The initial recommendation was to keep Auto. Subsequent discussion weighed its
switching/refinement complexity against these results and favored **PNG as the
default**, with SVG available explicitly and further Auto work deferred. The
benchmarks do not establish a clear overall advantage for Auto over PNG. They
also expose a much larger cold-checkpoint penalty that neither image format
removes. Completed cursor prewarming resolves the tested late-curve burst, at an
explicit preparation cost. The 4 MP PNG ceiling remains a resource bound, not a
proven optimum; display-density/resolution policy needs separate evaluation.

The [6 November real-document follow-up](2026-11-06-realistic-codecs.md) revisits
that policy judgment with papers/slides, sustained sharpness observations and
an experimental Auto classifier. It identifies both SVG typing regressions and
a useful SVG zoom advantage; the earlier discussion is not evidence that Auto
has no worthwhile use case.

[Compact evidence](2026-11-01-codecs.json) contains per-session observations,
backend/source/runtime hashes, nearest-rank summaries, power snapshots, and
validation results. Raw traces and samples remain in ignored `artifacts/`.

## Method and engine inputs

- Apple M1 Pro, 8 cores, 16 GiB, macOS 15.7.9, TeX Live 2026, VS Code 1.143.1,
  Node 26.12.0. Accepted samples use AC power, low-power mode 0. Native processes
  are headless. Matrices run serially, without concurrent builds or TeXstudio
  measurement jobs. All inputs are local; no Tectonic or dependency downloads.
- Same imported engine production source, compact MuPDF 1.28.5/ICU 78.3 objects,
  and **identical XeTeX worker SHA-256** for both builds. The preview PNG path uses
  either system zlib 1.2.12 level 1 or native-API zlib-ng 2.3.3 level 2. MuPDF's
  other uses of system zlib keep their existing ABI. Builder/profile/library
  hashes are recorded. Dependency libraries were reused, rather than rebuilt
  from a fresh toolchain.
- Imported engine changes include pagination retention and convergence fixes,
  recovered-EOF handling, current Web2C primitives/format persistence, safe cold
  destinations, malformed-DVI error handling, optional larger PNG budgets, and
  the new compressor. Both worker and frontend were rebuilt together for the
  changed internal handshake/format. The measured manifest records engine
  `1620b15`; `1b895fc` adds only the corresponding activity-test API update.
- Eight fixtures: sparse prose, dense prose, dense TikZ, and mixed image/math,
  each in nominal 1- and 30-page versions. TikZ has 625 circles and 625 line
  segments on first/middle/last pages. The mixed image is a deterministic local
  gradient with synthetic noise, not a representative photograph.
- Main matrix: **128 fresh sessions**, 32 warm-ups excluded, leaving 3 sessions
  per fixture/mode/backend cell. Each source ends identically across modes and
  repetitions. Main comparison retains the extension's **4,000,000-pixel cap**.
  Profiling body is 800 × 700 CSS pixels; the measured page viewport is
  785 × 663, DPR 2. Initial PNGs are 1570 × 2221; actual dimensions are retained.
- End-to-end timings start at an action/source-mutation request and end two
  animation frames after a matching mount ACK, or after revealing a valid
  resident surface. This is a paint opportunity. VS Code application startup,
  physical keyboard dispatch and GPU/display completion are separate boundaries.
  Initial preview includes native capability probing/startup and source sync.
- Paced edits await their paint; rapid tests use open-loop input. Cursor
  prewarming is deliberately absent from the ordinary matrices and explicitly
  completed in the final control. First edits and warmed edits are separated.
  Edits within a session are correlated; 3 sessions per cell support local
  comparisons, not precise population-level rankings of 1–3 ms differences.

## Full-page PNG: the encoder improvement is real

Native medians in ms; seven nearby widths (1600–1606), with no encoded export
cache hits. Export includes raster drawing and encoding, excluding compilation,
startup and browser work. Quantiles span these nearby sizes, rather than seven
independent sessions at identical dimensions.

| Fixture | System export | zlib-ng export | System encode | zlib-ng encode |
| --- | ---: | ---: | ---: | ---: |
| dense-1 | 14.1 | 9.2 | 11.3 | 6.8 |
| tikz-1 | 31.1 | 19.7 | 18.9 | 7.1 |
| mixed-1 | 54.9 | 30.4 | 49.0 | 24.6 |

Decoded RGB matches exactly: **252 PNGs validated, 147 matching-output
comparisons**, including default and larger caps. At this size, text payloads
shrink from about 213 to 189 KiB and TikZ from 329 to 321 KiB. The synthetic
mixed raster grows from 1716 to 1773 KiB; at 3200 pixels it grows about 6%.
This is a faster lossless encoder, not a universal file-size reduction.

The backend-only end-to-end ablation is smaller for warmed typing: system/new
PNG medians are 27.8/24.4 ms sparse, 27.8/26.7 dense, 877.3/878.6 TikZ, and
27.8/28.3 mixed, for 30-page documents. Tiny patches spend little time encoding;
large compiler costs and frame scheduling dominate other cells.

## End-to-end mode comparison

Warmed letter insertion medians, ms, in the 30-page fixtures. Each cell pools
four warmed letters from each of three sessions; the first letter is excluded.

| Fixture | PNG | SVG | Auto |
| --- | ---: | ---: | ---: |
| sparse-30 | 24.4 | 21.7 | 21.0 |
| dense-30 | 26.7 | 27.4 | 27.8 |
| tikz-30 | 878.6 | 855.1 | 864.1 |
| mixed-30 | 28.3 | 39.9 | 29.4 |

The 1-page versions show the same pattern: about 21–28 ms for ordinary text,
PNG/Auto about 28–29 ms versus SVG 40 ms on mixed content, and roughly 0.85–0.87 s
when typing before the expensive TikZ figure. Image format does not eliminate
that figure's interpreter work.

First preview medians, ms, for the 30-page fixtures:

| Fixture | PNG | SVG | Auto |
| --- | ---: | ---: | ---: |
| sparse-30 | 532.8 | 458.7 | 433.5 |
| dense-30 | 474.7 | 505.7 | 534.1 |
| tikz-30 | 1496.3 | 1506.7 | 1505.6 |
| mixed-30 | 753.7 | 667.1 | 638.8 |

Startup has substantial compiler/session variance, so these small samples do
not establish a universal first-render winner. Dense Auto first shows PNG and
usually reaches SVG another **0.4–0.44 s** later, including the production
350 ms idle delay. Sparse Auto starts directly as SVG. Mixed Auto stays PNG.
First paint and settled/refined paint remain separate in the evidence.

The first edit is a different cost again: approximately 280–330 ms for plain
prose, 440–490 ms for mixed content, and 1.28 s for TikZ in these unprewarmed
sessions. The warmed table is not a guarantee for arriving at a new edit site.

Warm text updates transfer about **248 bytes for PNG dirty rectangles** and
**385 bytes for SVG DOM patches** in the long fixtures. Mixed SVG instead sends
about **1.15 MB** per update. Its embedded `<image>` element is outside the
allowlist in `media/preview-svg.js`, so it stays an isolated SVG image and
receives no DOM patches. This is an extension renderer limitation, rather than
an inherent requirement of SVG. Supporting safe embedded image resources in the
retained DOM is the clearest next rendering opportunity.

Navigation measurements now account for continuous scrolling: a resident page
can become visible without a new image ACK. Cached-next-page operations with no
new image frames occur in the measured runs. Zoom measurements separate immediate
scaling from sharper replacement; magnification separates immediate local
content from the sharp native tile. All 96 measured main sessions make **zero
native requests for the three small lens moves**. PNG makes a new request for a
large move; SVG uses a DOM clone or its local SVG image, according to the actual
renderer path.

## Rapid input and the remaining spike

Rapid matrix: **48 sessions**, 12 excluded warm-ups, leaving 36 measured.
Each burst inserts 12 letters or backspaces at 100 ms intervals. TikZ also changes
the curve eight times at 125 ms intervals. All 81 measured phases meet the input
cadence and visibility checks; no preview errors. Prose can coalesce the first
few inputs during its cold initial edit, then keeps up.

Median last-key-to-paint after the typing burst, ms:

| Fixture | PNG | SVG | Auto |
| --- | ---: | ---: | ---: |
| sparse-30 | 26.9 | 21.8 | 24.5 |
| dense-30 | 25.7 | 31.9 | 26.5 |
| tikz-30 | 886.7 | 869.4 | 882.8 |
| mixed-30 | 30.4 | 39.0 | 29.8 |

The TikZ burst paints no intermediate source generations: 11 of 12 inputs are
coalesced, then the final image arrives about 0.87–0.89 s after the last key,
roughly 2 s after the burst starts. Backspace has the same problem here.

Paced curve editing initially looked much faster, but its first edit is still
about 0.9 s; only the next edits fall to roughly 35–55 ms. Native traces explain
the distinction: cold/rapid changes repeatedly restore a prefix around
9.57 million token positions, rather than reaching the late curve checkpoint.
A completed first edit establishes the more useful checkpoint; an interrupted
burst does not establish it in time.

A focused control calls the **production `prepareEdit` API** at the coordinate
location, waits for `ready`, then sends the same burst. Twelve sessions, three
warm-ups excluded, all cadence/visibility checks pass:

| Mode | Unprepared final-key ms | Prepared final-key ms | Preparation ms |
| --- | ---: | ---: | ---: |
| PNG | 883.4 | 54.8 | 1054.0 |
| SVG | 910.9 | 55.2 | 1037.8 |
| AUTO | 894.9 | 41.8 | 1042.7 |

All eight prepared coordinate edits paint, with zero coalesced inputs. Preparation
costs about a second beforehand: the work moves earlier. A cursor visit shorter
than that preparation time can still leave a cold edit. This points to checkpoint
readiness/retention and interrupted work as the next latency target, rather than
another codec change. Edits before the entire figure still need the figure's
computation.

## Resolution and memory

With a 16 MP session opt-in, requested widths are honored below the larger cap.
Native zlib-ng full-page export medians, ms:

| Fixture | ~1600 wide | ~2240 wide | ~3200 wide |
| --- | ---: | ---: | ---: |
| dense-1 | 9.8 | 17.8 | 31.7 |
| tikz-1 | 19.6 | 29.4 | 50.0 |
| mixed-1 | 29.9 | 58.4 | 115.2 |

These correspond to approximately 3.6, 7.1 and 14.5 MP. Under the default 4 MP
cap, the two larger requests instead produce 1681 × 2378. The extension's
validation limit stays 4 MP in this pass; the density probe uses its own bounded
raw protocol reader. A 16 MP browser RGBA surface alone costs 64 MB, versus
16 MB at 4 MP, before other buffers/caches. Better compression does not remove
the rasterization, decoded-memory or upload costs. Visible-region detail rendering
and SVG remain useful for zoom.

Native viewer lifetime peak footprint medians, MiB, over the complete long-document
scenario, including adjacent-page caches, zoom/detail and magnification:

| Fixture | PNG | SVG | Auto |
| --- | ---: | ---: | ---: |
| sparse-30 | 77.6 | 58.4 | 58.8 |
| dense-30 | 78.8 | 62.3 | 62.9 |
| tikz-30 | 77.3 | 52.8 | 65.5 |
| mixed-30 | 70.9 | 67.3 | 70.8 |

Sampled viewer/worker task sums are about 244–278 MiB across these cases; shared
and copy-on-write pages are counted in each task, so this is not unique physical
RAM. Browser DOM/canvas/heap counters are retained separately, rather than
presented as total Chromium/GPU memory.

Auto's dual representation has a cost: dense-30 transfers about 4.62 MiB over the
whole scenario, compared with PNG 2.90 and SVG 3.39; TikZ is 6.66 versus 4.88 and
4.62. Those totals include navigation, zoom and lens images. Warm Auto text/vector
edits already use SVG patches; it does not render PNG then SVG for every key.
On mixed content it follows the PNG path and avoids the full-SVG typing penalty.

## Changes and validation

- Adopted the shared engine fixes and pinned/static native-API zlib-ng in the
  macOS builder and manual GitHub Actions workflow, including license and
  capability/version checks. Standalone system-zlib builds remain available.
- Kept the default codec and pixel budget. The local demo bundle uses the new
  tested pair; the old bundle is preserved. These local outputs use ad-hoc
  signatures; the updated notarization workflow has not been dispatched here.
- Corrected profiler assumptions about continuous-page cache navigation,
  region/detail ACKs, SVG-image magnification, and source/runtime provenance on
  resume. Repairs affected excluded warm-ups. Every accepted main session uses
  the same repaired harness. The long interrupted regression run is excluded.
- 58 engine integration tests pass; 199 unit tests, 13 native build/signing-helper
  tests, 11 XeTeX behavior/format-cache-migration tests, native rendering/safety/
  protocol groups, lint, production VSIX contents and final actual VS Code
  preview acceptance pass. The controlled decode fixture now gates its intended
  image, preventing an already queued neighbor from consuming the delay. The
  matched-build reproduction helper was executed end to end offline and produced
  byte-identical frontend and worker executables to the measured zlib-ng pair.

## Reproduction

Use supplied clean/local sources with `native/scripts/build.py` for a new compact
zlib-ng bundle. For an encoder-only pair, reuse an existing compact build's static
MuPDF/ICU objects and its matching manifest:

```sh
python3 scripts/profiling/build-codec-pair.py \
  --reuse-work /path/to/native/.work/build-directory \
  --dependency-bundle /path/to/its/bundle \
  --zlib-ng-source /path/to/locked/zlib-ng \
  --icu-prefix /path/to/icu78.3 \
  --work native/.work/new-codec-pair \
  --bundle-prefix native/.bundles/new-codec-pair
```

The helper checks locks, profiles and host library versions, records reused
library hashes, and asserts equal XeTeX worker hashes. Set absolute binary paths
in the variants JSON:

```sh
npm run compile-tests
export VSCODE_EXECUTABLE='/Applications/Visual Studio Code.app/Contents/MacOS/Code'
export TEXPRESSO_BINARY=/absolute/new-codec-pair-zlib-ng/bin/texpresso
export TEXPRESSO_PROFILE_VARIANTS='[
 {"name":"system","binary":"/absolute/new-codec-pair-zlib/bin/texpresso","codecs":["png"]},
 {"name":"ng","binary":"/absolute/new-codec-pair-zlib-ng/bin/texpresso","codecs":["png","svg","auto"]}
]'
TEXPRESSO_PROFILE_OUTPUT="$PWD/artifacts/new-codecs" \
TEXPRESSO_PROFILE_PAGES=1,30 TEXPRESSO_PROFILE_KINDS=sparse,dense,tikz,mixed \
TEXPRESSO_PROFILE_REPEATS=4 TEXPRESSO_PROFILE_EXTRAS=1 \
node scripts/test-integration.cjs --profile-auto

node scripts/profiling/png-density.cjs --output artifacts/new-density --sample-memory 1
```

For rapid/control runs, use only the `ng` variant. Set scenario `rapid-e2e`, pages
`30`, extras `0`, repeats `4`, and the four kinds for the first run. Use only
`tikz` plus `TEXPRESSO_PROFILE_COORDINATE_PREWARM=1` for the control. Choose new
output directories. Run each matrix serially. Finally:

```sh
node scripts/profiling/summarize-codecs.cjs \
  --main artifacts/new-codecs --rapid artifacts/new-rapid \
  --density artifacts/new-density --prewarm artifacts/new-prewarm \
  --output docs/profiling/new-codecs.json
```

The summary checks cohort sizes, equal final source hashes, unique session keys,
consistent measured harnesses, visibility/cadence, lens-request bounds and pixel
validation. Detailed frames, native stages and memory observations remain in the
raw directories identified by hashes in the evidence.
