# Preview profiling — 22 October 2026

The two changes from this pass are a faster lossless PNG encoder and immediate
explicit page/format requests. PNG remains the default. With those changes, PNG
is competitive with SVG for ordinary text and faster for the denser text cases
in the browser; SVG remains useful for vector zoom and magnification.

The complete corpus covers 1, 10 and 100 pages, at three text densities and with
complex TikZ pages. There are five fresh native sessions per case and codec:
120 sessions before and 120 after, plus 40 production-webview browser cases on
each side. The [reproduction guide](README.md) defines the timing boundaries;
[the compact results](2026-10-22.json) retain p50/p95, per-page edit values and
native stage measurements. Full raw traces and generated documents remain in
local `artifacts/profile-*` directories.

Measurements used an Apple M1 Pro with 16 GiB RAM, macOS 15.7.9, Node
v26.12.0, TeX Live 2026, and the locked compact MuPDF 1.28.5 build. All work
used local packages; OS and package caches were warm. The browser was Chromium
155 at DPR 2 with an 800 × 700 CSS-pixel preview. Its local binary HTTP bridge
replaces VS Code IPC; browser action timings include that bridge and two animation
frames after the image swap, rather than a GPU-completion timestamp.

## Export cost and frame size

These are retained-display-list exports of the one-page fixtures at a requested
1600-pixel raster width, approximately a Retina preview 800 CSS pixels wide.
The actual PNG is 1599 × 2261 pixels. SVG geometry is independent of this width.
Values are median milliseconds and KiB; SVG bytes are uncompressed wire bytes.

| Page content | PNG export before → after | SVG export after | PNG KiB before → after | SVG KiB |
| --- | ---: | ---: | ---: | ---: |
| sparse | 39.4 → 9.9 | 2.0 | 93 → 74 | 108 |
| dense | 54.0 → 13.2 | 2.8 | 303 → 213 | 333 |
| packed | 64.7 → 15.9 | 3.4 | 453 → 314 | 493 |
| tikz | 58.9 → 29.9 | 4.2 | 275 → 320 | 559 |

Sparse, dense and packed text span approximately 16%, 58% and 88% of the
available text height. The TikZ page has 625 circles, 625 segments, a curve and
two paragraphs. In longer TikZ documents, figures appear on the first, middle
and last pages; intervening pages contain prose.

The original PNG path spent most export time in compression. The replacement
streams unfiltered scanlines through fast deflate, using a scanline, a 64 KiB
output block and zlib state. It checks every RGB pixel and uses 8-bit grayscale
only when all channels agree exactly. One colored pixel keeps the entire page
in RGB. Drawing, color mapping and fidelity fallback policy are unchanged.

Four real pages compare pixel-for-pixel against the old output, and their SVGs
are byte-identical. Native regressions also cover noise, padded strides,
checksums, one-pixel images, resolution and a single colored pixel in an otherwise
neutral page. Colored TikZ PNGs grow about 16% in return for faster compression;
neutral text PNGs become smaller. Separate RGB pilots compared None/Sub/Up
prediction and zlib's run-length strategy; the alternatives used more time or
bytes on this corpus.

First-page latency stays nearly constant with document length. TeX/package/font
startup dominates text startup, and TikZ compilation dominates the figure's
first render. Faster image export therefore yields a modest startup saving,
compared with the larger improvement in repeated updates.

One freshly copied development bundle took 3894 ms on its first startup smoke
check. A subsequent fresh-process PNG check took 476 ms and SVG 397 ms; image
export itself remained a small part of startup. This single cold-bundle
observation is separate from the warmed five-run matrix above and does not
establish the cause of the extra startup time.

The long tail on ordinary text edits includes rebuilding an early compiler
checkpoint. TikZ edits cost around 0.8 seconds even with SVG, while native
DVI interpretation and SVG export each take only a few milliseconds. Rendering
is a small fraction of that figure-edit delay.

A supplemental ten-page probe moved the text marker after the figure and prose.
It ran three fresh sessions per codec. After the first edit established a nearby
checkpoint, subsequent text edits took **46.7 ms PNG / 20.5 ms SVG**
(p95 84.6 / 25.9 ms). The first edit at a new position could still
cost 0.8–2.0 seconds. This makes compiler rollback/checkpoint coverage the next
valuable investigation, especially around expensive TikZ loops. The current
fence calculation deliberately backs up and rounds source offsets in 64-byte
blocks; changing that needs correctness work around TeX's buffered input and
macOS's existing font-loading/fork constraints.

Editing an early page also invalidates later output. Returning to the last page
after editing the first costs the work to recompile the intervening suffix:

## Browser display and page navigation

The production webview had applied its 100 ms zoom/resize debounce to explicit
page and format choices too. Those actions now send immediately; gestures retain
the debounce. The table is a return to already compiled page 1 in ten-page
documents, measured from the page control to the paint opportunity. Values are
p50 / p95 milliseconds. PNG rasters are 1569 pixels wide in this viewport because
of the vertical scrollbar; SVGs use the same CSS page size and DPR.

| Content | PNG before | PNG after | SVG before | SVG after | Decode PNG / SVG after |
| --- | ---: | ---: | ---: | ---: | ---: |
| sparse | 174 / 182 | 36 / 58 | 132 / 133 | 32 / 1049 | 2.2 / 5.5 |
| dense | 196 / 198 | 42 / 49 | 144 / 163 | 48 / 52 | 2.7 / 16.3 |
| packed | 214 / 216 | 47 / 50 | 160 / 165 | 57 / 59 | 3.2 / 24.2 |
| tikz | 200 / 213 | 64 / 65 | 151 / 153 | 43 / 50 | 3.3 / 12.7 |

The sparse-SVG p95 contains one 1049 ms navigation sample taken while the UI
was being inspected. Its DVI/export stages took about 2 ms, HTTP frame transfer
5 ms, and image decode 9 ms; the delay occurred elsewhere. A follow-up used an
8-second settling delay, one warm-up pair and five measured sessions per codec,
with no UI inspection during measurement. PNG navigation took
40.1 / 46.7 ms
and SVG 23.7 / 27.3 ms
(p50 / p95), with no one-second stall. The original sample remains in the
main table and raw results; the repeat does not identify the precise cause.

SVG's cheap native export shifts work into the browser. Outlined SVG decoding
and layout rises with text density: thousands of glyph-use elements still need
parsing and placement. PNG decode is much cheaper. Warm canvas draw/readback
probes also cost more for the dense SVG cases; those timings include readback
synchronization and are separate from the action timings.

After the changes, PNG wins the denser text navigation cases here. SVG wins
sparse text and this vector drawing, and preserves sharp zoom/magnification
without asking the engine for new rasters. PNG retains the bounded-pixel path
and fidelity reference. SVG transfers larger uncompressed frames in these
fixtures; gzip/shared-glyph experiments remain possible future work, with browser
parsing still a separate cost. These results support retaining the PNG default
and the toolbar toggle while testing more image-heavy and remote workloads.

## Memory

A separate three-session, twenty-export probe used macOS kernel lifetime peak
physical-footprint counters, so brief allocations survive the 50 ms sampling
interval. These are median **viewer process** peak MiB, excluding XeTeX workers.

| Page | PNG before | PNG after | SVG after |
| --- | ---: | ---: | ---: |
| sparse | 43.7 | 34.6 | 28.2 |
| dense | 44.4 | 35.8 | 28.0 |
| packed | 44.4 | 36.6 | 28.1 |
| tikz | 45.1 | 37.3 | 28.1 |

The PNG change saves roughly 8–9 MiB of peak viewer footprint at this raster
size. SVG avoids that native raster buffer but still incurs browser geometry,
image-cache and raster/GPU costs. Encoded size and SVG's intrinsic dimensions
are not measurements of browser image memory.

The 100-page full-session traces show the existing XeTeX snapshot workers
dominate process-tree accounting:

| Content / format | Viewer sampled peak MiB | Peak sum of task footprint MiB | Peak task count |
| --- | ---: | ---: | ---: |
| sparse PNG | 35.7 | 243.0 | 13 |
| sparse SVG | 25.8 | 233.4 | 13 |
| dense PNG | 39.5 | 251.7 | 14 |
| dense SVG | 30.8 | 246.2 | 15 |
| packed PNG | 41.8 | 257.5 | 15 |
| packed SVG | 33.7 | 247.1 | 14 |
| tikz PNG | 44.1 | 307.1 | 17 |
| tikz SVG | 35.3 | 296.9 | 17 |

The task sums include copy-on-write/shared accounting and are not a deduplicated
RAM total. Sampled peaks can miss brief allocations; the first memory table uses
the separate kernel high-water counter. There is no evidence here of retaining
one raster per visited page: the viewer retains its current display list and
page-sized working buffers. The browser traces include V8 heap diagnostics;
full Chromium/GPU and production VS Code IPC memory remain separate measurements.

## Validation and follow-up

The changes pass 60 extension unit tests with compile/lint, 13 real-engine tests,
and the native PNG, SVG, provider and incremental-DVI regressions. The generated
page comparison checks all RGB pixels and byte-identical SVG. The final browser
suite completed all 40 cases with the requested codecs, using production assets.

The next focused performance work is compiler checkpoint/fence behavior for
first edits and small edits inside expensive figures. For SVG, measuring a more
compact glyph-use serialization and compressed transport would address different
costs: parsing/layout and wire bytes respectively. Pixel budgets and image
lifetimes should remain part of any browser/GPU memory investigation.
