# Cursor checkpoint prewarming, 22 October 2026

This experiment uses the rich three-page demo, the production controller and
renderers, actual VS Code webview IPC, Auto rendering and automatic auxiliary
reruns. Each fresh session inserts the exact text ` It works instantly` after
`Edit this sentence and watch the preview change.` at nineteen fixed 100 ms
intervals. Input never waits for a render. This answers the ordinary typing
question directly; earlier rich-demo measurements inserted four separate chunks
and waited for their first paints.

The three conditions are a cold first insertion without a settled cursor,
preparation completed before typing, and typing beginning 80 ms after the browser receives the host notification
that `preview-prepare` was sent. The last condition records
the native-command-send to source-application interval using timestamps from the
same extension-host clock. It does not compare browser and host clock origins.
Each input updates its simulated document version and cursor position through the
production `prepareEdit` entry point. Continued typing resets the ordinary cursor
idle timer.

The harness associates every input with the actual source-barrier acknowledgment,
records first matching changed-source paint, per-input exact/caught-up paint,
last-key latency, canceled/superseded frames, and stale/intermediate paints. Only
page-zero frames may finish the page-zero typing phase; neighboring-page frames
cannot do so. Its paint endpoint is two animation frames after a decoded frame,
not compositor presentation. Cadence is valid only with at most 20 ms timer
lateness and an observed span within 20% of the scheduled 1800 ms; the webview
must remain visible. Profiling-only Chromium background-throttling flags are
used as in the prior rapid-input experiment.

Controller regressions separately cover cursor idle scheduling, foreground
decode priority, bucket deduplication, retargeting and source-edit cancellation,
stale acknowledgments, optional capability gating, hidden/paused previews,
unchanged page/cache/UI state, and PNG/SVG patch-base preservation. Synchronization
tests cover UTF-8 offsets in an included file through its existing engine alias,
invalid offsets, unrelated documents and no overlay reopening. The protocol
boundary rejects malformed preparation acknowledgments.

Reproduce using the prepared local demo bibliography and native bundle:

```sh
npm run compile-tests
TEXPRESSO_PROFILE_SCENARIO=prewarm-e2e \
TEXPRESSO_PROFILE_OUTPUT="$PWD/artifacts/profile-prewarming-new" \
TEXPRESSO_PROFILE_CODECS=auto TEXPRESSO_PROFILE_REPEATS=1 \
VSCODE_EXECUTABLE='/Applications/Visual Studio Code.app/Contents/MacOS/Code' \
TEXPRESSO_BINARY="$PWD/native/.bundles/darwin-arm64-preview/bin/texpresso" \
node scripts/test-integration.cjs --profile-auto
node scripts/profiling/prewarm-summary.cjs artifacts/profile-prewarming-new
```

Use a fresh output directory; `TEXPRESSO_PROFILE_PREWARM_MODES=cold,warm,early`
selects the conditions. No dependencies are downloaded. The controlled continuous
webview acceptance preface runs once before native-backed profiling.

## Initial cancellation finding

The first three sessions used engine `2fd6802b5974e173f2c55210a8bfd64ad7f2cecf`;
their [separate snapshot](2026-10-22-prewarm-initial.json) preserves that identity.
Completed preparation moved the first acknowledged-source paint from 667 ms to
44 ms and painted all nineteen source sequences. However, typing during
preparation exposed another cold replay after the first current frame: this led to a targeted fix that preserves a still-useful preparation fence when
a following edit does not require a real root rollback. The sustained typing
measurements below check that handoff separately under overlapping edits. The original early run also had a 437 ms final-key tail; it
retained its earlier checkpoint but spent 315 ms between compiler checkpoints
and 67 ms in SVG export. That tail alone does not establish another preparation
attempt. Only the initial prepare and a cached request after typing were sent.


## Final measured build

The final three conditions used engine
`4919c95cc8da0a3baafbf204ef7b87b079074e58`, binary SHA-256
`706c367f61b09588e7dab2608c1eebd2aaa2801483731392ce799be27db2ce09`,
with VS Code 1.143.0. All three phases remained visible and met the 100 ms input
cadence criteria; maximum timer lateness was 4.6 ms. No preview errors or stale
paint opportunities occurred. The continuous-webview acceptance preface passed
again, including retained rollback geometry and magnifier/detail ownership.

| Condition | First key caught up | Last key painted | Inputs without an exact intermediate paint |
| --- | ---: | ---: | ---: |
| No settled cursor | 761 ms | 58 ms | 12 of 19 |
| Prepared before typing | 56 ms | 59 ms | 0 of 19 |
| Typed during preparation | 659 ms | 55 ms | 11 of 19 |

Preparation completed in 526 ms during cursor dwell. It moves the cold work
before typing rather than eliminating it. The warmed session painted all
nineteen acknowledged source versions in approximately 56–60 ms per key. The
first key is a space and can reuse identical image content; the following `I`
produced its changed frame in 58 ms. SVG patches and content references remained
in use. This is one session per condition, sufficient to demonstrate the cold
versus prepared behavior here, not a statistical latency distribution.

The early first input was applied 86.6 ms after native preparation was sent.
Cancellation was sent immediately and acknowledged 89.8 ms later. Warm and early
preparation preserved toolbar page, scroll position, rendering choice and the
hidden normal status line. Early typing still showed two cold root replays,
including another replay after its first current-source frame. The ordinary cold
condition also showed two. Native inspection identified the shared path:
`engine_end_changes` calls `compute_fences(trace = 0)` during a real root restart;
that clears the retained fence and returns without replacing it. The targeted
fix covers the simpler cancellation handoff when no actual root rollback
supersedes it. Consequently this run does not establish smooth first typing
when preparation is interrupted, despite that correctness regression and the
fast final key. The final snapshot retains full
checkpoint/rollback measurements so that remaining cold path can be investigated.

Peak sums of the existing macOS per-task physical-footprint counters were
approximately 301/246/303 MiB for cold/prepared/early, with up to 18/8/18 tasks.
These counters are not PSS or a deduplicated physical memory total after fork;
they exclude VS Code renderer memory. No separate memory benchmark was run.
Owned viewers, samplers and isolated test Code processes exited at completion.
