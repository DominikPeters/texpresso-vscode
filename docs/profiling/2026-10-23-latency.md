# Remaining latency spikes: attribution and bounded improvements

This pass investigates the latency tails left after the reliability work. It separates engine work, host/webview delivery and decoding, successful browser commits, and the profiling observer's two animation-frame callbacks. None of these endpoints establishes compositor presentation.

## Baseline and measurement limits

The initial diagnosis uses `artifacts/profile-long-input-fix-final2/varied-30-auto.json`, the previous finite 1,464-input workload, and `artifacts/profile-codec-visual-final/` for the controlled codec comparison. The baseline native commit was `91f7d921d6769d104366b5fb36bd1b2abec2b17e`. The old artifacts contain source hashes and bundle metadata; they predate the additional stage instrumentation described below.

The historical `caughtUp` metric credits a visible frame for the source-follow page whose source sequence is at least that of an individual input. A later keystroke can already have made that frame stale when the observer reports it. Historical pixel-change gaps also include unchanged surfaces and the harness's deliberate 700 ms post-phase wait. Those original numbers are retained for provenance. New analysis adds separately named endpoints rather than rewriting old measurements.

Browser and host `performance.now()` values come from separate processes. Only browser-local durations, host-local durations and host round trips are compared. Recording both `timeOrigin` values does not calibrate one-way IPC latency. Source-input timestamps describe real VS Code `editor.edit` operations, not physical keyboard or compositor latency.

A separate source-page/viewport-page mismatch causes avoidable render churn. In the old controlled PNG prose comparison, 202 inputs produced 605 image headers and 92.41 MB of payload. There were 190 same-source/revision/page PNG pairs at widths 1078 and 970 pixels. The first-width members accounted for 32.12 MB. Auto had 183 such pairs and 30.38 MB of first-width payload. These are observed baseline costs, not a prediction of the improvement from changing request selection.

The mismatch occurs when forward SyncTeX changes the requested page while the controller retains a render width belonging to the viewport's other active page. The next viewport update then requests the correct page width. The largest middle-paragraph scheduling gap uses a single width, so this churn is an independent improvement opportunity rather than its demonstrated cause.

## Additional stage instrumentation

The opt-in profiling harness records host image posts, post completion, successful decode ACKs, event-loop heartbeat delays, and browser scheduler/long-task samples. Browser commit timing records image receipt, successful commit and ACK preparation. The two-rAF observer records its own callbacks separately. Geometry-based page visibility and `document.visibilityState` are distinct observations.

`latency-summary.cjs` reports:

- The historical individual-input catch-up endpoint, explicitly allowing a frame that is stale relative to later inputs.
- A source-current observer endpoint, and a stricter source-and-compiler-revision-current observer endpoint where that metadata exists.
- Successful visible commit ACKs independently of rAF sampling. The strict endpoint also requires the frame to remain current against the host sequence and compiler revision when the ACK arrives. Browser-current commits are retained as a separate, weaker observation.
- Typing-only progress intervals ending at the last edit completion, with open pixel-change intervals marked censored. Post-phase work is reported separately.
- Browser-local receive-to-commit and commit-to-rAF durations, plus host post-to-ACK round trips. No cross-clock one-way delay is inferred.

To inspect either an old or a newly instrumented raw result without modifying it:

```sh
node scripts/profiling/latency-summary.cjs \
  artifacts/profile-long-input-fix-final2/varied-30-auto.json \
  /tmp/texpresso-latency.json
```

### Visibility and latency

Each run contains a roughly one-second hidden-document interval: about 14,515.6–15,517.9 ms before and 6,788.3–7,799.1 ms after. JavaScript heartbeat lag stays around 1 ms and no long-task entries are reported. Hidden documents can delay animation-frame callbacks while script processing continues. The old observer's visible paint samples alone could miss a whole hidden interval. This newly observed behavior does not prove that the old uninstrumented middle-paragraph gap had the same cause.

All-input metrics remain unchanged. An additional sampled-visible subset requires a preceding visible sample, no hidden sample through the current commit ACK, and no observation gap above 150 ms. Older artifacts lack immediate visibility-change events, so this cannot exclude brief hidden intervals between observations. Sparse exposure is unknown, not assumed visible.

The strict ACK endpoint requires a geometrically visible page in a visible browser document at commit, with source sequence and compiler revision still current in the host at ACK receipt. It bounds commit latency; it does not establish compositor presentation. One finite before/after pair supports fewer redundant renders and lower routine latency. The maximum is not eliminated, and these numbers do not establish a universal p95 improvement.

For owning visible prose commits, browser-local receive-to-commit medians are 2.9 ms before and 2.8 ms after, with p95 values of 5.1 and 4.2 ms. Host post-to-ACK round-trip medians are 3.93 and 3.69 ms. Commit-to-two-rAF observation adds medians of 12.4 and 11.8 ms. Thus normal decoding and mounting are small compared with the largest catch-up intervals.

The remaining 444.3 ms visible tail starts at source sequence 62, at 9,803.393 ms. Its page-1 PNG header arrives at 9,923.723 ms, after 120.330 ms, including a 51.030 ms export. Further inputs arrive. A sequence-65 page-1 image commits at 10,208.649 ms but is already stale; the first strict current page-1 ACK is sequence 66 at 10,247.688 ms. That final image's browser-local receive-to-commit cost is 1.4 ms. This spans repeated work and superseded epochs, not a 444 ms decode.

## Final longer-workload check

`artifacts/profile-latency-long-final/varied-30-png.json` contains the complete 1,464-input PNG workload using the corrected controller and the new native build, commit `8576d13a041b40ae21de2fba1f262d2ec241ceb2`. The native frontend hash is `9141aae5a37249ce9d41c82ad240f056edacdd46a9c3eefb8d412da0f2d6a471`; the controller runtime hash is the same corrected module listed above. The run exited cleanly. Every sustained phase met its intended 100 ms cadence; maximum input lateness was 3.8 ms. Both five-probe clean reference-oracle rounds passed (10/10). ### What still causes the largest delays

**Source-page priority and superseded work.** The early 358.6 ms strict catch-up interval starts at sequence 78, at 11,586.319 ms. Page-0 requests continue while forward SyncTeX identifies page 1. A sequence-79 page-1 PNG header is ready at 11,801.219 ms, but that request produces no decoded ACK in the interval. Page-0 images continue to receive ACKs. The first strict current page-1 ACK is sequence 81 at 11,944.907 ms; its browser render time is 3.6 ms. This resembles the remaining 444 ms matched-run tail: repeated compiler/render work and active-page priority changes consume the interval, rather than a large decode.

The next concrete rendering opportunity is to keep the source-follow render target distinct from the viewport's toolbar/center page. Currently forward SyncTeX may choose adjacent visible page 1, then a viewport report chooses center page 0 again and retires the render intent. A useful older-source page-1 frame can consequently be rejected even though page 1 remains visible. The width correction removes an independent redundant render, but does not redesign this priority state. Any further change must retain stale-link/source-navigation protections and manual scrolling behavior.

**Compiler replay for undo.** Undo begins at 162,227.989 ms. The compiler rolls back from 26,545,029 to 17,480,731 tokens, replaying about 9.06 million tokens. Forward SyncTeX returns at 162,474.239 ms; the PNG header arrives at 162,497.075 ms, after 269.087 ms, including 20.240 ms export. The visible commit ACK follows at 162,506.781 ms, after 278.792 ms. Two-rAF observation adds another 10.896 ms. Better checkpoint coverage or restoration/reuse around the reverted source remains relevant; ordinary image decoding is not the bottleneck here.

**Forking and compiler bursts under scheduling pressure.** The included-return 160.0 ms tail starts at sequence 1390. There is a 21.93 ms checkpoint fork, repeated budget/wait compiler bursts and another keystroke before a sequence-1390 frame completes. Sequence 1391 exports in 3.208 ms and commits with 1.6 ms browser render time. The 21.93 ms fork is a wall-clock observation, not isolated CPU time. Small compiler scheduling budgets improve opportunities to process input but cannot preempt an individual fork or synchronous operation.

**Worker startup and convergence.** The trace now explicitly records initial worker handshake at 199.4 ms and prewarm startup at 161.8 ms. Later changed-aux convergence respawns take about 165–170 ms, including roughly 162–165 ms handshake, during recovery/oracle phases. These startup operations remain synchronous. The timings explain a previously unmeasured cost; they do not justify claiming every replay starts at the root or every convergence pass is unnecessary.

The remaining priorities are therefore source-target versus viewport-page scheduling, checkpoint coverage for large undo, and reducing synchronous worker-start/replay costs. The new trace can distinguish those from browser decode and observation delays.

## Validation

The final changes pass 187 unit tests, 50 native engine tests and six C suites, plus full ESLint, production VSIX packaging/content checks and actual VS Code preview acceptance. The actual-Code acceptance includes startup, source barriers, adjacent continuous pages, SVG/PNG patches, magnifier ownership, unsaved updates, hide/restore and Stop. The canonical local demo bundle and ZIP use the tested `8576d13` pair; the earlier `91f7d92` bundle is preserved for the matched comparison. The compact machine-readable results are in [2026-10-23-latency.json](2026-10-23-latency.json).
