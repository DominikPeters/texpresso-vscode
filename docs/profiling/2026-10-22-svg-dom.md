# Retained SVG rendering and PNG dirty rectangles — 22 October 2026

This implements the SVG path proposed in the [caching follow-up](2026-10-22-caching.md).
The extension now mounts a validated static SVG DOM and applies bounded updates.
PNG dirty rectangles are a measured prototype; native PNG updates remain full frames.
The [measurement snapshot](2026-10-22-svg-dom.json) accompanies this report.

## Implemented SVG behavior

The existing PNG/SVG toolbar selection remains. Selecting SVG uses retained DOM
for supported static path-based output. Unsupported SVG uses the existing isolated
SVG image decoder, and the existing engine/decoder PNG fallbacks remain available.
No native source, wire protocol or bundle changes are needed for SVG DOM patches.
TeXpresso still compiles and exports a complete SVG to the extension.

The extension indexes XML spans, normalizes standalone font paths, and computes
small child splices against the SVG content identity acknowledged by the webview.
It sends the patch with fresh revision, source sequence, bounds, links and
destinations. Source invalidation disables interaction with the old page until
an updated frame is accepted. A missing base or failed patch requests full bytes
from the encoded cache. Hiding/reloading the webview resets its acknowledged base.
The single frame/decode credit also applies to patches.

Unchanged nodes stay mounted. The page and magnifier use separate ID namespaces;
the magnifier clones the current SVG and rewrites its local references. Cached
SVG pages stay mounted in bounded opacity layers so navigation does not rebuild
their SVG layout. Eviction removes the layer. A two-entry prepared-document cache
also avoids repeating canonicalization/indexing for cached output. Frames whose
viewport was superseded can still populate the encoded cache if their revision,
source sequence and requested page remain valid.

## Stable glyph identities

MuPDF's encounter-order font IDs change when an earlier font is introduced.
For standalone font paths containing only `id` and `d`, the extension instead uses
an identity derived from the exact outline: a 128-bit prefix of SHA-256, encoded
with URL-safe base64. It explicitly compares outlines on a digest collision and
abandons normalization if unequal paths would alias.

Equal outlines share one definition, in deterministic ID order. Each original
`use` retains its transformation, paint and text metadata. This is exact geometry
reuse rather than a claim that two fonts are interchangeable. Other definitions
and SVG features keep their original IDs and behavior. A font change that alters
layout broadly can still require a full frame.

The longer stable IDs make full frames about 3–13% larger in these fixtures.
In exchange, the ordinary typing updates below are usually **385 bytes**, and
introducing `\textbf{New font}` before existing text uses about **9.5 KB** rather
than replacing the old glyph references throughout the page. Payload counts here
exclude the fresh frame/annotation metadata.

## Validation and resource limits

The browser accepts only static SVG/defs/groups/paths/uses/rectangles/clips/masks
and vetted attributes. References must be local, IDs unique, and paint URLs local.
Active elements, event handlers, CSS, external references, embedded images, DTDs
and unsupported content stay out of the inline renderer. This preserves the
isolation needed when moving beyond
[SVG image-mode processing](https://w3c.github.io/svgwg/specs/integration/).
All patch fragments, paths, ID/reference accounting and overlap constraints are
checked before the visible DOM changes. Inert text metadata is never interpreted
as a resource reference.

Limits are 2 MiB of SVG text, 20,000 elements, depth 32, 64 patch operations,
256 affected nodes and at most 64 KiB of patch data or 35% of the full frame.
Indexing/canonicalization checks a 20 ms elapsed-time budget; diff generation
checks 5 ms. These checks do not preempt an individual JavaScript operation.
Budget failures use full-frame/image fallbacks. Zero-count reference entries are
removed so repeated edits do not accumulate obsolete identities.

The prepared-document LRU holds at most two entries and an estimated 8 MiB,
accounting for encoded bytes, UTF-16 text and indexed nodes. The active and pending
models also have the per-document text/node limits. The existing page cache holds
at most eight images / 8 MiB; the webview cache holds at most four entries with
32 MiB of estimated accounting. SVG opacity layers can retain compositor surfaces;
these estimates and counts are not exact browser/GPU memory limits. A magnifier
clone exists only while it is in use.

## Measured SVG updates

Chromium 155, DPR 2, 800×700 CSS-pixel preview, on the same M1 Pro as the earlier
reports. Two fresh sessions per content type and mode, ten-page fixtures, five
unique one-letter insertions and two backspaces per session. The baseline uses
the existing decoded-image cache and disables SVG DOM through a harness-only
capability override. The final comparison includes extension-side indexing,
canonicalization and diff generation. Intermediate pilot runs are not used in
the snapshot's comparison table.

The controller column is elapsed time handling the frame in the extension,
including hashing, canonicalization, cache work and diff generation. Webview time
runs from message dispatch to acknowledgment, including validation and DOM update
or image decoding. These are elapsed times, not CPU utilization. End-to-end rows
in the snapshot also include compilation, the local HTTP bridge and two animation
frames after swapping the page; they do not measure GPU completion or VS Code IPC.

| Content | Image-mode webview ms | Retained webview ms | Retained controller ms | Typical typing patch bytes |
| --- | ---: | ---: | ---: | ---: |
| sparse | 5.9 | 1.8 | 2.0 | 385 |
| dense | 18.1 | 2.7 | 7.8 | 385 |
| packed | 26.0 | 3.8 | 10.1 | 385 |
| tikz | 14.4 | 2.5 | 11.0 | 385 |

**39/40** one-letter updates used patches in this final run. An indexing-budget
fallback accounts for the remaining update. The normal isolated-image path remains
valid under that fallback. Cached image fallbacks are reused directly on navigation.

Adding a font before the page's existing text:

| Content | Image-mode webview ms | Retained webview ms | Patch bytes |
| --- | ---: | ---: | ---: |
| sparse | 7.6 | 3.4 | 9529 |
| dense | 20.0 | 6.6 | 9529 |
| packed | 30.5 | 4.8 | 9529 |
| tikz | 19.1 | 3.6 | 9529 |

All eight tested font additions used patches. Full initial DOM mounts remain more
expensive than decoding images, particularly on nearly full text pages. There is
no universal end-to-end speedup: native compilation times varied substantially
across these sequential runs, and the expensive TikZ loop still dominates those
edits. The controller/webview columns isolate the work targeted here. PNG remains
the default; both toolbar options remain useful.

## PNG: update one opaque rectangle on a canvas

The equivalent PNG technique is to retain a page bitmap and replace the rectangle
covering every changed pixel. The rectangle includes erased old ink, not just new
marks. A persistent canvas keeps this bounded and avoids accumulating overlay
images. The
[Canvas API](https://html.spec.whatwg.org/multipage/canvas.html) supports drawing a
small decoded image at an offset in an existing bitmap.

The probe renders old/new pages with the actual engine, compares their pixels,
encodes the bounding rectangle as a small PNG, and applies that crop over the old
page. It verifies exact reconstruction in Node and checks full canvas RGBA pixels
in Chromium. Insertions, undo/erasures, paragraph reflow and a moved TikZ control
point are covered. The reflow fixture replaces the first lipsum paragraph with
literal prose and expands an early word into a longer phrase.

| Case | Rectangle area | Full PNG bytes | Crop PNG bytes | Browser full image / crop update ms |
| --- | ---: | ---: | ---: | ---: |
| sparse-letter | 0.03% | 55,086 | 546 | 3.65 / 1.40 |
| sparse-reflow | 5.38% | 56,914 | 29,990 | 2.95 / 1.40 |
| dense-letter | 0.03% | 197,317 | 546 | 3.25 / 1.15 |
| dense-reflow | 5.38% | 198,760 | 29,990 | 3.30 / 1.40 |
| packed-letter | 0.03% | 300,566 | 546 | 3.95 / 1.45 |
| packed-reflow | 5.38% | 301,854 | 29,990 | 4.75 / 1.45 |
| tikz-letter | 0.03% | 294,130 | 1,000 | 4.15 / 1.25 |
| tikz-reflow | 5.34% | 295,729 | 47,832 | 4.20 / 1.40 |
| tikz-coordinate | 4.51% | 293,838 | 113,538 | 4.40 / 2.50 |

Browser inputs are preloaded. Timings include decode and canvas drawing; seven
measured insert/undo pairs follow two warmup pairs. Pixel readback checks happen
outside the timed intervals. A complete canvas redraw was also measured and is
recorded in the snapshot. Small crop updates take roughly **1–2.5 ms**, versus
**3–5 ms** for full image updates in these samples.

The larger opportunity is avoiding full PNG compression and transfer. Implement
comparison and crop encoding **before compression in TeXpresso**, using the new
raster that was already drawn. Decoding and recropping a complete PNG in the
extension would add work after full rendering/encoding had already been paid.
The probe's Node scan/encode values are warm-buffer JavaScript/zlib measurements,
not native-engine performance predictions. Its PNG helpers intentionally support
only the opaque, unfiltered 8-bit Gray/RGB output used in this bundle.

A native implementation would retain one previous RGB raster: about **10.3 MiB**
at the tested 1599×2261 resolution, up to **11.4 MiB** at the four-megapixel limit.
It would still pay for drawing the new raster. Use a confirmed base identity,
integer pixel offsets, bounded dimensions and a full-frame reset when size,
bounds, theme or format changes. Begin with one rectangle and a full-frame cutoff
for broad changes; consider tiles only after measuring their additional encoding,
decoding and composition costs. PNG updates are a worthwhile native follow-up.

## Correctness checks and reproduction

74 unit tests, 15 native-engine tests, compilation, lint and the exact VSIX payload
check pass. The actual VS Code integration suite loads the SVG module inside a
webview and checks node reuse, scoped clones, stale-base rejection and active
content rejection, then exercises cached navigation, unsaved source edits and
hidden-tab restoration. It now observes page decode acknowledgments instead of
assuming every cache hit emits a new native render request.

The standalone browser validation checks original native SVG pixels against the
canonicalized/patched result for text, TikZ and the demo's equations, colors,
title fonts and hyperlinks. It also checks clips, magnifier clone pixels, adjacent
splices, transactional failures, scoped IDs and inert metadata. PNG canvas region
updates reproduce every tested full-frame pixel. All engine tests/probes use
headless/dummy video; existing local TeX Live is used without downloads.

```sh
npm run compile-tests
TEXPRESSO_PROFILE_CODECS=svg TEXPRESSO_PROFILE_REPEATS=2 \
  TEXPRESSO_PROFILE_DISABLE_SVG_DOM=1 npm run profile:preview:browser -- artifacts/svg-before-new
# Open http://127.0.0.1:9383 and run, then stop this server.
TEXPRESSO_PROFILE_CODECS=svg TEXPRESSO_PROFILE_REPEATS=2 \
  npm run profile:preview:browser -- artifacts/svg-after-new
# Run again, then stop this server before starting another timing probe.
node scripts/profiling/svg-diff.cjs artifacts/svg-validation-new --math
node scripts/profiling/svg-diff-browser.cjs artifacts/svg-validation-new
# Open http://127.0.0.1:9384/validation and run the checks.
node scripts/profiling/profile-regions.cjs artifacts/png-regions-new
node scripts/profiling/png-regions-browser.cjs artifacts/png-regions-new
# Open http://127.0.0.1:9385 and run the comparison.
```

Use a new output directory each time and set `TEXPRESSO_BINARY` to override the
existing local bundle. `npm run demo:preview` opens the real editor demo; select
SVG in its preview toolbar to try the retained renderer.
