# Auto rendering end to end — 22 October 2026

Auto is a responsiveness/vector-quality tradeoff rather than a general speedup
over manual PNG or SVG. The first PNG is useful while a denser page's SVG is
prepared after idle. After learning the page, ordinary SVG edits can use small
DOM patches. PNG dirty rectangles make manual PNG very competitive for typing.
Expensive TikZ edits still spend most of their latency in compilation.

## Interpreting Auto versus SVG

The small warm-typing differences between Auto and explicit SVG do not establish
an Auto performance penalty. Inspecting all eight measured warm frames per mode
in each dense-1, dense-100 and tikz-100 cell shows that both modes used retained
SVG DOM patches. Auto had already learned the page and requested SVG directly.
Both native paths perform the same SVG preflight/export; the Auto selection
branches add little work. These edits did not render PNG and then SVG.

For dense-100 warm edits, extension-host SVG processing was approximately 4 ms
in both modes, and webview dispatch-to-decode/apply was approximately 2 ms in
both. The wait from acknowledgment to the two-animation-frame paint endpoint
varied by several milliseconds. With only two independent sessions per cell,
1–3 ms end-to-end ordering differences should not drive chooser thresholds.
The larger TikZ timing differences also include compiler/session variability.

The actual extra Auto cost occurs on unknown pages which take the PNG-then-SVG
path, and formerly in the decoded-cache issue below. It provides an early image
and later vector quality at the cost of two representations. The foreground
rendering stages can benefit even when compiler/startup variance hides that in
the total: in dense-1 startup samples, PNG native export was about 13 ms and
webview delivery/decode/apply about 7 ms; SVG export was about 1.4 ms but its
initial webview mount about 44 ms. These small-sample component measurements are
not a general first-paint guarantee and exclude compilation.

Warm PNG updates deserve a separate comparison: its host processing was about
0.06 ms versus about 4 ms for SVG in the measured dense cases. SVG DOM patches
save transport and retained-DOM work, but a complete SVG is still exported from
the native process, transferred to the extension, parsed/canonicalized, and
compared there on each edit. A tiny webview patch does not imply a tiny amount
of upstream processing. PNG still draws the whole page before comparing pixels;
the crop primarily saves encoding, transfer and image-update work.

Priorities suggested by these observations:

1. Investigate checkpoint/rollback reuse, especially text before/after expensive
   figures and the first edit following startup. This targets hundreds of ms.
2. Profile and reduce repeated SVG parsing/canonicalization/diff work. This
   targets the measured roughly 4 ms host cost without sacrificing vector output.
3. Calibrate Auto using native export, host and browser costs, with compiler work
   separated. Its present budgets test whether SVG is acceptable, rather than
   whether it beats the available PNG path. Require a sustained difference and
   hysteresis before switching; the current small Auto/SVG gaps are insufficient.
4. Test inputs arriving at fixed intervals while compilation/rendering remains
   in flight. The current paced scenario waits for each paint, so it cannot
   establish staleness or responsiveness during a rapid typing/dragging burst.
   Zoom/magnifier behavior, mixed image/vector pages and browser/GPU memory
   should also be measured before changing the general default.

## Decoded-cache improvement

The baseline exposed a concrete problem: Auto kept both a transient PNG canvas
and the SVG which superseded it for the same page/source revision. The conservative
32 MiB decoded-cache budget could then evict a neighboring page’s SVG. Returning
to that page resent its full SVG (383,887 or 570,613 bytes), while manual PNG/SVG
already used a zero-byte decoded cache reference.

The webview now forgets that temporary PNG only after a valid inline SVG is ready
for the same page, revision and source sequence. Failed/stale replacements do not
discard it. Manual format choices retain their existing behavior. The host can
still retain bounded encoded frames for fallback.

A focused navigation-only rerun used the same browser/fixtures, four sessions per
density, with repetition 0 excluded. It did not run concurrently with the VS Code
matrix. The old full scenario and the focused rerun share the exact navigation
prefix; the later typing operations are omitted in the follow-up.

| Auto previous-page return | Before ms | After ms | Before image bytes | After image bytes |
| --- | ---: | ---: | ---: | ---: |
| dense-10 | 53 | 26 | 383887 | 0 |
| packed-10 | 75 | 30 | 570613 | 0 |

Every previous/next decoded-cache revisit in the follow-up transferred zero image
bytes, including warmup. The fix passes 83 unit tests, type checking, webpack,
lint and VSIX packaging/asset validation. The 36-case actual VS Code baseline and
the eight-case production-webview follow-up complete successfully.

The next useful performance targets are compiler checkpoint reuse for expensive
figures and SVG canonicalization/diff work on warm text edits. This pass leaves
Auto’s codec thresholds and idle delay unchanged.

## Measurement boundaries

The browser matrix uses the production controller, native engine, SVG DOM/PNG
canvas renderers, and page caches over the local HTTP/SSE profiling bridge.
There are four fresh sessions per codec and sparse/dense/packed/TikZ ten-page
fixture; the first repetition is excluded as warmup, leaving three sessions per
cell. Codec order rotates between repetitions. Browser DPR is 2 and the preview
is 800 × 700 CSS pixels, with actual raster dimensions recorded per frame.

The second matrix uses actual VS Code webviews and `postMessage` IPC, with the
same production assets, native engine, scenario, and a fixed 800 × 700 CSS-pixel
preview document. It covers dense text and TikZ in one- and hundred-page
fixtures, with three sessions per codec; repetition 0 is warmup, leaving two
measured sessions per cell. Only one extension-host window is launched for the
matrix, plus a fresh window for the unfinished cases after a harness timeout. Source changes are injected through the extension's document-sync API.

Timings start at a preview action/source mutation request and end two animation
frames after the matching main-page decode/update acknowledgment. Startup includes
capability probing, native startup and root-buffer synchronization. Detail-region
ACKs and stale source generations cannot finish an operation. The endpoint is a
paint opportunity, not GPU completion or physical display scanout. Initial VS Code
application startup and keyboard-event routing are outside the timing boundary.

`firstPaintMs` measures the first matching visible update. `settledPaintMs` is the
last matching main-page paint during the observation window, including idle SVG
refinement. Eligible operations are observed for at least 650 ms after first paint
and until received main frames finish decoding. Ordinary typing waits 80 ms after
paint before sending the next edit; this tests paced typing, not an overlapping
high-speed input burst. The final edit in a sequence has an idle observation.
The 350 ms Auto idle delay is intentionally included in refinement latency.

OS/TeX caches are warm and no TeX packages or native dependencies are downloaded.
Native processes run headlessly. The machine is an Apple M1 Pro with 16 GiB RAM
and local TeX Live 2026. Both PNG and SVG use the new incremental update paths.
The length matrix runs after the browser matrix, rather than concurrently.
There were brief TypeScript compilation/unit-test runs while the browser baseline
was collecting; the separate actual-VS-Code pass runs without concurrent builds.
Small sample counts and correlated edits make these local observations, not
population latency estimates.

## Memory and work

A 50 ms process-group sampler records viewer and compiler-worker footprints,
kernel viewer lifetime peaks, and sampled CPU counters. Native RSS/footprint sums
include shared/copy-on-write pages and are not deduplicated physical RAM.
Transient workers can escape sampling. Browser heap readings are diagnostics,
not a VS Code/Chromium/GPU memory total. Image-byte totals exclude frame metadata
and IPC overhead; SVG patch JSON is included.

The profiler now records process-group IDs explicitly and converts Mach CPU ticks
using `mach_timebase_info` (125/3 on this host). Older samples from this experiment
had ticks in a field named `cpuNs`; their metadata records the timebase and the
summarizer converts them. Prior memory measurements are unaffected. Native-stage
wall times remain a separate measurement from sampled CPU work.

## Reproduction

```sh
npm run compile-tests
TEXPRESSO_BINARY=/path/to/texpresso TEXPRESSO_PROFILE_SCENARIO=auto-e2e \
TEXPRESSO_PROFILE_CODECS=png,svg,auto TEXPRESSO_PROFILE_REPEATS=4 \
node scripts/profiling/browser.cjs artifacts/auto-browser
# Open http://127.0.0.1:9383/ and press Run preview profiles.

VSCODE_EXECUTABLE='/Applications/Visual Studio Code.app/Contents/MacOS/Code' \
TEXPRESSO_BINARY=/path/to/texpresso \
TEXPRESSO_PROFILE_OUTPUT="$PWD/artifacts/auto-vscode" \
TEXPRESSO_PROFILE_PAGES=1,100 TEXPRESSO_PROFILE_KINDS=dense,tikz \
TEXPRESSO_PROFILE_REPEATS=3 \
node scripts/test-integration.cjs --profile-auto

node scripts/profiling/summarize-auto.cjs artifacts/auto-browser artifacts/auto-vscode
```

Raw frames, operation timings, native stages and memory samples are retained in
ignored `artifacts/profile-auto-*` directories. The accompanying compact JSON
records the summary statistics and input revisions.
