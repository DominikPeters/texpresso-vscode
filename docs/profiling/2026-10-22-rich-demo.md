# Rich-demo typing latency, 22 October 2026

The expanded demo exposed compiler work that the earlier plain-text corpus did
not capture. The exact source is `scripts/preview-demo/showcase.tex`, including
cleveref, hyperlinks, bibliography, mathematics, and a later-page TikZ figure.
The benchmark inserts ` It works instantly` immediately after “Edit this
sentence and watch the preview change.” on page one.

## Native findings

The delay is reproducible without a browser. With automatic reruns disabled,
one run measured a first edit at 1105 ms and subsequent edits at 68–82 ms. The
first edit rolled back to token zero; warm edits resumed a checkpoint at token
18,842,782. Most of the first-edit cost therefore precedes rendering: the
compiler repeats the preamble and package loading. PNG export was only around
20–30 ms in that run.

Automatic reference convergence introduced a second, avoidable cold path.
The old convergence check only recognized a byte match against an auxiliary
buffer created by a previous convergence pass. It did not recognize matching
`.aux`/`.out` files already loaded from disk. Consequently an idle finishing
pass could discard every checkpoint and start another compiler even though
references were already stable. Typing after a pause then sometimes cost
391–1196 ms; the next nearby edit could be fast again.

The native fix also recognizes byte-identical filesystem input:

- A backtrackable flag records that the initial input came from the filesystem.
- Comparison uses the cached bytes that were consumed, never a fresh disk read.
- LaTeX's normal end-of-pass reread of its own newly written aux file does not
  erase evidence of the initial input. Matching final output to that initial
  input establishes the same fixed point even when the pass reads its output.
- New or changed output keeps the existing stash-and-rerun behavior.
- Editor-owned/convergence-owned buffers retain their existing handling.

The focused regression uses real TeX input/output primitives with a prebuilt
auxiliary file. Identical input reaches convergence immediately; changing the
writer still makes the next compiler read the changed auxiliary value.

## Final native sample

With automatic reruns enabled and the fix applied:

| Operation | Source to complete native PNG |
| --- | ---: |
| First edit after startup idle | 532 ms |
| Next edit | 39 ms |
| Next edit | 39 ms |
| Edit after another 1.6 s idle | 44 ms |

The after-idle edit retains the 18.84-million-token checkpoint instead of
restarting at zero. Logs confirm both `showcase.aux` and `showcase.out` are
unchanged from their original filesystem inputs. This is one independent native
session, not a browser-frame latency claim. Other runs varied in startup and
cold compile duration, so the first-edit numbers do not establish a speedup.

It is useful as a same-build-layout confirmation of the recurring cold path.

## First edit remains a separate limitation

The edited sentence is near source offset 640. On macOS, TeXpresso deliberately
waits for DVI output before making its first automatic fork, because system-font
initialization after a fork can be unsafe. In this document the initial
checkpoints are already around source offset 2048, after the edited paragraph.
The first paragraph edit therefore has no earlier usable checkpoint. Once an
edit establishes an adaptive fence near offset 576, the preamble can be reused.

A checkpoint made after the first page cannot retroactively represent the
preamble state. A cursor-idle preparation command could replay unchanged input
and place an explicit READ fence before the likely edit. Explicit fences already
bypass the automatic first-output guard during real edits, so this would use the
same fork assumptions as the existing first-edit path. It would move roughly
600 ms of work ahead of typing, rather than eliminate it. Such a command needs
to retain the visible frame, reuse checkpoints for nearby cursor positions, and
be preemptible when typing starts; font-sensitive documents still need explicit
validation. This pass leaves the periodic macOS guard intact; cursor preparation
is follow-up work.

## Reproduction

Generate the demo's local bibliography/reference files once with
`npm run demo:preview`. Then:

```sh
npm run compile-tests
TEXPRESSO_BINARY="$PWD/native/.bundles/darwin-arm64-preview/bin/texpresso" \
  node scripts/profiling/rich-demo-native.cjs artifacts/profile-rich-demo-new
```

The harness copies the exact demo source and its local `.bib`, `.bbl`, `.aux`,
and `.out` into isolated fixtures. It compares automatic reruns off/on, inserts
` I`, `t`, ` works`, and ` instantly`, and leaves 1.6 seconds for idle convergence
before the first and last edits. Idle waits are outside the reported operation
timings. `TEXPRESSO_RICH_RERUN=true` selects only the automatic-rerun case.

`richFixture(output, id)` is exported for the corresponding browser/VS Code
benchmark so both paths use the same corpus. No packages are downloaded and no
native preview windows are opened.

## Actual VS Code end to end

Four production continuous-preview sessions on native revision `7b13026` use the
same isolated demo corpus and edit chunks. Each mode/rerun combination has one
independent session. Timings end at a double-animation-frame paint opportunity,
not an OS compositor trace. Inputs are acknowledged with their actual source
sequence before a frame can finish an operation; an earlier auxiliary pass cannot
be mistaken for the edited source. The initial pass and third edit have a 1.6 s
idle observation window, matching the native experiment. Normal UI assertions
(the hidden status banner and stable `Auto` label) pass throughout.

| Mode | Automatic reruns | First edit | Next `t` | Next ` works` | After-idle ` instantly` |
| --- | --- | ---: | ---: | ---: | ---: |
| PNG | Off | 596 ms | 51 ms | 62 ms | 56 ms |
| Auto | Off | 581 ms | 64 ms | 61 ms | 81 ms |
| PNG | On | 607 ms | 48 ms | 68 ms | 77 ms |
| Auto | On | 579 ms | 59 ms | 66 ms | 78 ms |

These are **first paints containing the acknowledged edited source**. Automatic
reruns still do background work: the third edit's later page-zero paint was at
584/599 ms for PNG/Auto, and the after-idle edit's later paint was at 610/594 ms.
The edited text was already visible much earlier. The result establishes that
warm and after-idle editing can remain responsive during convergence; it does
not establish that convergence work has disappeared. The approximately 0.6 s
first edit remains visible in actual VS Code and is not an SVG-versus-PNG problem.
One session per configuration is insufficient for small codec comparisons.

## Post-profile checkpoint restoration fix

The four-case VS Code timing matrix above used native revision `7b13026`.
A targeted late-include check then exposed an existing rollback invariant:
returning from a completed stable pass to a live snapshot restored saved output
buffers but left input read counters and derived DVI/SyncTeX page metadata at the
completed pass. Editing a file first read after that snapshot could crash.
Native revision `7f3d752` now restores those counters and derived outputs together.
The regression completes a stable pass, edits the included file twice, checks
that the PNG changes, and verifies both SyncTeX directions on the second page.
All 24 headless engine tests pass. The original timing matrix is retained with
its original engine revision; final-binary acceptance is recorded separately.

## Final build validation

A separate single Auto session with automatic reruns enabled used native
`7f3d752832d3de75d79408a839d1e132f281063f` (binary SHA-256
`839c449ed58ca3bf1043f8e3bd67df1a51bd3b14c66f649fa7da6a2629db3e5b`).
The controlled continuous-webview checks above passed again, including rollback
geometry and shared magnifier/detail ownership. The native-backed rich document
then produced first edited-source paints at 606 ms for the first insertion,
63/69 ms for the next two, and 81 ms after idle. No preview errors or stalls
occurred; normal status remained hidden and the Auto label remained stable.

The later same-source auxiliary paints were still present, at 802 ms for the
third insertion and 615 ms after idle. The final restoration fix preserves the
fast warm path; this one validation does not replace the earlier four-case
measurements or establish that auxiliary work has gone away. The endpoint remains
a double-animation-frame paint opportunity after the acknowledged source frame,
not a compositor trace. The native viewer and sampler exited at completion.
